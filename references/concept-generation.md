# 概念生成协议

`stage-3a-concept.md` 规定概念长什么样；本文件规定概念**怎么来**。没有走完这五步的候选，不进概念卡。

## 概念模式契约（先读）

概念是用户还没做的决定。决策阶段与生产阶段的规则相反：

| | 生产阶段（S3b 之后） | 概念阶段（S3a） |
|---|---|---|
| 落盘 | 每阶段产物写文件 | **选定前不写任何文件**。三个候选只在对话里。用户选定后才写 `01_concept.md`，含选定概念、被否候选各一行与否决理由、检索记录 |
| 选择 | 模型按规则决定 | **模型不预选**。三个候选同等发展、各做一次 D2；可以推荐，但"最佳 / 已选 / top"在用户选之前禁止出现 |
| 示例 | 母版可实例化 | **示例禁止复用**。工作示例在 `examples/concept-worked-examples.md`，不在本文件，概念模式默认不读 |
| 过程 | 只交结果 | **过程可见**。交付消息先给一行 D0 处境清单、一行 D1 领域清单，再给候选。搜索有没有收窄，用户一眼能看到 |
| 停靠 | S5 后停 | 模糊级需求停两次：**处境选择**（D0 之后、D1 之前）与**候选选择**；已含处境的需求只停一次 |

用户说"存一下候选"时可写 `01_concept-candidates.md`，这是唯一例外。


## 为什么需要协议

模型在一个题目下会取最可能的答案。用户否决一个，模型从同一个中心再取一个。否决只改变输出，不改变分布。改变分布只能改输入：禁用默认值、注入真实细节、用约束堵死默认路径。

## 第 1 步 禁用（模型自己做）

写出这个题目下**最可能出现的 10 个前提**，全部列入本项目禁用表。要求写得具体到能一眼认出（"绝症"、"车站告别"、"翻旧照片"），不写抽象类别。之后任何候选命中禁用表即作废。

## 第 2 步 种子（模型自己生产，用户细节是加分项）

种子 = 具体到能拍的细节。模型直接"编一个细节"会退回套路（旧照片、一封信），所以种子不靠编，靠**搬**：从模型知识最密、最具体的地方搬现成的规则与痕迹。三个引擎，每次至少用两个，共产出 ≥ 6 颗种子，全部在模型内部完成，**不因为缺种子而停下问用户**。

**引擎 A：制度移植**（首选）
把题目的情感内核搬进一个有真实规则的领域，规则本身就是种子。领域清单（按题目现选 3 个，彼此距离远）：账号与订阅规则（家庭共享、双人套餐、紧急联系人）、宠物医院、健身房、驾校、物业与快递、银行密保、图书馆、学校家长群、餐厅预订、机场值机、医院陪护、殡葬以外的殡仪流程、租房合同、二手交易。写法："在〈领域〉里有一条规则：〈规则原文级别的具体〉。这条规则遇到〈情感内核〉会怎样？"

**引擎 B：骰子自转**
四张表（空间 / 物件 / 规则 / 谁不知道什么）各随机抽一项拼成一句骨架，抽 5 次，自己按第 4 步标准淘汰到 2 个。表按题目现编，每张 ≥ 6 项，每项必须是可拍的具体物。示例表在 `examples/concept-worked-examples.md` 文末（只示形式）。用户看不到抽取过程。

**引擎 C：物件履历**
挑一件日常物件（不许是照片、信、日记、录音），写它三年的使用痕迹：谁买的、谁改过设置、哪里磨损、最后一次被用来干什么。痕迹里的人就是种子。

**引擎 D：检索（有 WebSearch 时必用，且在引擎 A 之前；无则跳过并标 `[未核实]`）**

搜索有三种粒度，只有前两种有用，且顺序固定：

| 粒度 | 做什么 | 查询写法 | 结果 |
|---|---|---|---|
| **D0 内核展开（D1 之前，不搜索）** | 把情感内核展开成 ≥ 6 个互不相同的处境，防止直接跳到默认处境 | 见下方"内核展开" | 处境清单，每条一行 |
| **D1 题材发现（先做，2–3 次）** | 让领域清单来自外部而不是模型默认 | 每条查询对应**不同的处境**与**不同的查询形式**（见下方"查询形式"） | ≥ 8 个领域，每个一行"领域 + 该领域的一条制度接触点" |
| **D2 规则核实（后做，每个选中候选 ≤ 1 次）** | 核实候选依赖的那条规则 | "〈领域〉 〈规则关键词〉 规定" | 证实 / 修正 / 推翻 / 未核实 |
| D3 事件级 | **禁止** | — | 只会得到别人的故事或榜单 |

**内核展开（D0）**：对"为什么会〈情绪〉"至少写 6 个互不相同的答案，每个是一种处境，不是一个故事。悲伤的爱情不等于分手。通用轴（任何情绪都先过一遍）：

| 轴 | 爱情 / 悲 的处境示例 |
|---|---|
| 分离 | 分手、异地、移民、服役、服刑 |
| 失去 | 死亡、失智、失语、失明 |
| 不能 | 已婚、阶层、宗教、家庭反对、年龄差 |
| 时间 | 老去、错过、太晚、倒计时 |
| 隐瞒 | 秘密、双重身份、假装不知道 |
| 照护 | 一方成为另一方的护理者、监护人、翻译 |
| 制度 | 签证、户口、医保、探视规定、遗产顺位 |
| 错认 | 认错人、被当成别人、名字重合 |

**处境停靠（模糊级需求必做）**

模糊级 = 需求里只有情绪和关系，没有处境、领域、物件或场所（"男女爱情，悲"是；"失智的丈夫认不出她"不是）。模糊级需求在 D0 之后、D1 之前停一次，把处境交给用户选，因为搜索方向是决定，决定归用户。

问法（一个问题，多选，6–8 项，按轴分组，每项附一行"会长出什么样的故事"，末尾留"你定"）。先给一行格式约束，让用户在目标格式下选。有 AskUserQuestion 工具时用它（multiSelect），否则在消息里编号列出。示例形式：

```
格式约束：30 秒 · 单 clip · 单人高强度表演 · 台词 1–2 句
选 1–3 个处境（或"你定"）：
1 失去 · 失智 —— 一方每天重新认识另一方
2 照护 · 翻译 —— 只有她听得懂他，但医生要本人回答
3 制度 · 探视 —— 名单只认直系亲属，他们没领证
4 时间 · 倒计时 —— 约定的日期到了对方还没来
5 隐瞒 · 病历 —— 一方假装没看见
6 分离 · 签证 —— 到期日在婚礼当天
7 你定
```

选后规则：D1 只在所选处境里做（仍 ≥ 2 条查询、不同形式）；只选一条处境时，第三个候选仍必须放进不同容器；用户说"你定"则按原规则取 ≥ 3 条不同轴。已含处境的需求跳过此停靠，直接把需求里的处境作为 D0 结果之一，再补 ≥ 2 条不同轴。

**默认处境（爱情题里是分手）最多占一条查询。**

**查询形式（D1 每条查询用不同形式）**：手续型（"〈处境〉 需要 办 的 手续"）、职业型（"哪些 职业 会 遇到 〈处境〉"）、制度型（"〈处境〉 规定 实务"）、场所型（"〈处境〉 最 常 发生 在 哪里"）、纠纷型（"〈处境〉 常见 纠纷 案例"）。两条查询不得共用一半以上的词。

**示例查询（仅示形式，禁止照抄；校验脚本会拦）**："失智 配偶 照护 手续 实务"（照护 × 手续型）、"探视 规定 家属 范围 实务"（制度 × 制度型）、"分手后 还要 一起 处理 的 事 实务"（分离 × 手续型）。

**D1 的好来源与坏来源**：律师实务文、政务号问答、法院判例摘要、消费者投诉汇总、行业操作手册是好来源，它们具体、有规则、没有故事。情感类自媒体、"N 个感人故事"、影评是坏来源，它们是套路的集合。查询里加"实务 / 规定 / 手续 / 纠纷 / 指南"能把结果推向好来源。

**D1 之后引擎 A 只能从 D1 的清单里选领域**（模型默认领域只在 D1 不可用时作为备选）。选 3 个彼此距离最远的做移植。

**D2 的四种处理**：证实 → 把查到的具体措辞写进种子；修正 → 按真实规则改候选，真实规则通常更奇怪，优先采用；推翻 / 未核实 → 换规则，或标注"规则为虚构，片中需自洽"，不得冒充真实。

**禁止**：搜"创意 / 点子 / story ideas / 短片 idea / 剧本灵感 / 感人"。
**预算**：一轮 ≤ 5 次（D1 两次 + D2 三次）。只依赖搜索摘要，不抓全文；摘要矛盾时取更新日期的并注明。
**落盘**：`01_concept.md` 末尾"检索记录"表：粒度（D1/D2）/ 查询 / 产出（领域清单或规则结论）/ 来源链接。

**用户细节（可选）**
交付候选时附一句："这些候选的种子是〈引擎〉产出的；如果你有一件真的见过的小事，替换进去会比任何一个都好。"用户给了就重跑第 3 步。用户说"想不出来"不影响流程，因为流程本来就不依赖它。想帮用户找的话给这七问（七选一即可）：相册里不是为了发出去拍的那张里有什么；上一条没回的消息说了什么；房间里哪件东西坏了还在用；熟悉的职业有哪条外人不知道的规矩；今天离你最近的陌生人手里拿着什么；这周烦的一件小事；父母一个自己没意识到的习惯。

**仍然禁止的种子**：一张旧照片、一封信、一段录音、一本日记、一个梦。

## 第 3 步 情境（不是故事）

生成 **10 个情境**。情境 = 一条规则或一个持续状态，不是一次事件：

- ✅ "一对夫妻只在给对方留便签时用敬语"
- ✅ "他离婚后仍每天用没交回的钥匙替前妻浇花"
- ❌ "他在车站追上了她"（这是事件，不生故事）

10 个情境必须在四个轴上拉开，每个轴至少出现 3 种不同取值：**谁**（关系）/ **在哪**（空间）/ **什么物件** / **什么被隐瞒**（谁不知道什么）。至少 2 个情境必须至少用到 1 颗种子。

## 第 4 步 评分

五条标准各 0–2 分，总分 < 7 丢掉：

| 标准 | 2 分 | 0 分 |
|---|---|---|
| 具体 | 一句话能说出画面里的物件与动作 | 只有情绪词 |
| 不可预测 | 听到前半句猜不到后半句 | 前半句已经决定了后半句 |
| 有代价 | 人物为此失去一样可见的东西 | 只是心情 |
| 能被讲成笑话 | 换个语气就是个笑话 | 只能哭着讲 |
| 没见过但立刻信 | 陌生但符合人的行为 | 见过一百次，或不信 |

评分写出来，不只写总分。

## 第 5 步 发展

取总分最高且**两两距离最远**的 3 个情境（至少两个轴不同），各配一个不同的透镜，按 `stage-3a` §3a.4b 格式写成候选。第 3 个必须放在**不悲（或不属于核心情绪）的容器**里：婚礼、玩笑、庆祝、例行公事。

## 常见失败

| 现象 | 原因 | 处理 |
|---|---|---|
| 10 个情境像一个 | 没在四轴上拉开 | 强制每轴换值再生成 |
| 候选都在禁用表边缘打转（"不是绝症，是慢性病"） | 禁用写得不够具体 | 禁用表按"观众会怎么概括这个故事"来写 |
| 种子没被用上 | 种子被当装饰 | 情境必须由种子推出，不是提到种子 |
| 三个候选主控画面相似 | 距离没拉开 | 换掉第 2、3 个 |
| 全部都太苦 | 没有容器反转 | 第 3 个强制放进喜庆容器 |

## 交付前自检（与 `scripts/validate_concept.py` 同一清单）

- [ ] D0 处境 ≥ 6 条，来自 ≥ 3 条轴；模糊级需求已让用户选过处境；默认处境最多进一条查询
- [ ] D1 查询 ≥ 2 条，两两共用词 < 50%，形式不同，没有一条与示例查询相同
- [ ] 3 个候选的主控画面是 3 个不同的物件或空间
- [ ] 3 个候选各做过 D2，结论写在候选的"风险"行
- [ ] 候选标题、种子、查询没有一个来自示例
- [ ] 消息里没有"最佳 / 已选 / top"；有一个推荐和一个问题
- [ ] 没有创建任何文件

选定落盘后：`python3 scripts/validate_concept.py 01_concept.md`。
